Usage rules

Triangle mark — Always inside a rounded-xl container (16px radius). Never freestanding. The triangle is a stroke-only SVG polygon, not filled.
Wordmark — "Prism" in Instrument Sans 700 with letter-spacing: -0.02em. Always paired with the mark. "by Obsrvr" may appear below in 400 weight, gray-400.
Minimum size — Mark: 28×28px. Full lockup: 120px wide. Never distort or recolor the mark outside the defined variants.
Clear space — Minimum clear space around the full lockup equals the height of the triangle mark.

Color rules

Emerald links — All clickable blockchain data (addresses, hashes, ledger numbers) use emerald-700 (#047857). Never blue.
Violet = Soroban — Contract calls, Soroban events, and smart contract badges always use the violet palette. This creates instant visual distinction between classic and Soroban activity.
No decorative color — Color always conveys meaning (status, type, interaction). Never use color just for visual variety.
Amber threshold — Amber appears when a metric is concerning but not critical (e.g., 57.3% crawler rejection). Red appears only for failures and errors.

Type rules

Mono for all blockchain data — Addresses, hashes, ledger numbers, amounts, fees, sequences, public keys. Never render these in the sans-serif face.
Sans for all UI text — Labels, descriptions, navigation, buttons, headings. Never use mono for UI elements.
Address truncation — Format: first 5–6 chars + "…" + last 4–5 chars. Example: GCGB2S...ZSTYH. Always pair with a copy-to-clipboard button.
Number formatting — Use comma separators for integers ≥1,000. Preserve full decimal precision for amounts. Use unit suffixes (K, M) only in charts and stat cards.

Data display principles

Human-readable first — Every transaction shows a natural language summary line before the raw operation details. Powered by SEP-41/SEP-50.
Progressive disclosure — Show the most useful data by default. Signatures, sequence numbers, XDR, and fee accounts are collapsed behind a "Technical" toggle.
Operations inline — Never separate operations onto a different tab or page. Each operation is a dense, typed row within the transaction.
Pattern detection — Annotate detected patterns: self-payment → "DEX routing", multi-hop → "swap path", same source/dest → "self-transfer".

Slide-out specs

Width: 480px in production (340px shown here for fit). Slides from right with a spring easing (300ms). Backdrop: bg-black/8 with 1px blur.
Ramp pattern — Inspired by Ramp's contextual panels. Shows entity preview without navigating away. Always includes "Open Full Page" CTA at the bottom.
Sticky header — Back button + close button stay pinned. Content scrolls beneath with bg-white/95 backdrop-blur.
htmx integration — Triggered via hx-get="/validators/{id}/preview" hx-target="#slideout". Panel content is a server-rendered partial.

Animation philosophy: Motion should be fast and subtle. Nothing bounces, nothing overshoots. Staggered fade-ups on page load (40ms between elements) create rhythm without delay. Hover transitions are ≤150ms. The only continuous animation is the pulsing live dot — everything else is triggered by user interaction or page load. All animations are CSS-only; no JavaScript animation libraries.

Dark Variant

The dark theme is used exclusively for marketing pages (coming soon, landing) and is never used in the explorer product. This creates intentional contrast: marketing feels premium and editorial, the explorer feels like a professional tool.

Dark variant rules

Background: #09090B — Near-black with a subtle blue tint. Surface cards use #12131A. Borders: #1E2030.
Accent: #7C6CF0 → #A78BFA — Purple gradient for the logo mark, headline accent, and interactive elements. Not emerald.
Text hierarchy — White (#fff) for headlines. rgba(255,255,255,.45) for body. rgba(255,255,255,.25) for tertiary. Never use gray-400/500 named colors.
No dark mode toggle — The explorer is always light. The dark variant is a separate design context for marketing only. Never mix them.
